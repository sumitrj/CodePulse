# The benchmark

For anyone who wants to reproduce or extend the numbers in the README.

Two harnesses over [SWE-bench Lite](https://www.swebench.com/) — 300 real
issues from 11 Python projects, each with the patch that actually fixed it.

| | asks | costs | status |
|---|---|---|---|
| `bench.run` | does the map point at the code that had to change? | minutes, free | **runs today** |
| `bench.exec_harness` | does an agent holding the map fix more bugs? | hours, containers, API spend | scaffolded, ungated by a real run |

## Why localization is the honest headline

CodePulse does not write patches. It answers *where* — so the number it should
live or die by is whether "where" is right. SWE-bench hands us that ground
truth for free: the gold patch names the files and functions the fix touched,
so scoring needs no LLM, no containers, and no human judgment. Two runs of the
same commit produce identical scores.

Resolve rate is the number people quote, and it is a different claim. It lives
in `bench.exec_harness`, it needs a container runtime and a paid model run, and
until someone runs it green **this project publishes the localization score and
claims no resolve rate.**

## Run it

```bash
python -m bench.run --limit 30
```

First run fetches the dataset (~25 MB, cached in `~/.cache/codepulse-bench`)
and shallow-fetches one checkout per instance. Later runs reuse both, and reuse
the index inside each checkout — which is why the timing column means
"retrieval", not "retrieval plus a cold index".

```bash
python -m bench.run --repos django/django --limit 20   # one project
python -m bench.run --instances astropy__astropy-12907 # one instance
python -m bench.run --arms bm25,pulse_map --k 1,5,10   # pick arms and cutoffs
```

Output lands in `bench/results/`: `scorecard.md` (the table) and
`results.json` (every instance, every arm, the top-20 ranking each produced —
enough to audit any row by hand). Only the scorecards are committed;
`results.json` is regenerated by the run.

## Why you should believe the numbers

A benchmark written by the tool's author is a self-report until specific things
make it checkable. These are the things.

**The oracle is checked against git.** `bench/truth.py` is the one component
whose bug would invalidate everything downstream — two real bugs have already
been found in it. So every post-fix file is rebuilt twice, once by us and once
by `git apply` on a scratch copy, and the two must be byte-identical:

```bash
python -m bench.validate            # all 300 instances
```

`tests/test_bench_validate.py` runs the same check on generated patches with no
network at all, across insertions, deletions, first/last-line edits, adjacent
and distant hunks, and every context width from 0 to 5. Patches there are
generated with `difflib` rather than hand-written, because a hand-written
fixture is a third implementation of the diff format and gets it subtly wrong —
the first draft of that file did, and git caught it.

One honest asymmetry: we are deliberately *more* tolerant of drifted hunk
headers than `git apply` is. Where git gives up, we keep searching for an exact
content match. So the test asserts our re-anchored output equals what git
produces from the *undrifted* patch — not that git accepts the drifted one.

**A floor and a ceiling, so the numbers can be read.** `recall@10 = 0.85` means
nothing on its own. The `random` arm shows what zero skill scores on the same
candidate set (deterministic — ordering is a hash of instance and path, not an
RNG). The reported **ceiling** is the fraction of gold files our own candidate
filter even offers; below 100% is a bug in this harness, not a limit of any arm.

**Intervals, not just point estimates.** Every arm is compared to `bm25` with a
paired bootstrap, and the scorecard prints the 95% interval on each difference.
When nothing separates, it says so in those words. At n=33 one instance is worth
about three points, so a "+7%" lead is two issues — the table is built to stop
you quoting that as a result.

**Nothing is tuned on this dataset.** BM25 uses the standard `k1=1.2, b=0.75`.
The map arm's seed weights and decay are coarse round numbers chosen once. Both
are constants at the top of `arms.py` and are meant to stay there — fitting them
to these instances would make the score a description of the fitting, not of the
tool.

**Caveat we own:** the seed extractor was fixed after watching it fail on a
sympy instance (it could not see bare lowercase identifiers like `ccode`). That
is legitimate development, but it means SWE-bench Lite has served as a
development set here, and a headline number really wants a set nobody has looked
at — SWE-bench Verified is the intended follow-up.

## The three arms

Every arm sees the issue text and the repo. None sees the gold patch — a test
asserts each arm scores identically on a redacted copy, so that isn't a promise,
it's checked.

- **`bm25`** — lexical retrieval over file text, identifier-aware, path tokens
  weighted. This is the baseline because it approximates what a grep-driven
  agent does: read the issue, search for its words. Parameters are the
  standard `k1=1.2, b=0.75` and are deliberately **not** tuned on this
  dataset, which would be fitting the test set.
- **`pulse_map`** — pull symbols out of the issue (traceback frames, backticked
  names, dotted paths), resolve them in the map, then walk the graph: whoever
  depends on a named symbol becomes a candidate even if the issue never names
  them. The graph walk is the claim under test.
- **`pulse_walk`** — the map arm done properly. Seeds *every* entity lexically
  rather than 40 regex-extracted names, then spreads activation greedily along
  edges. Two ideas carry it:
  - **Co-activation.** Each high-IDF issue term carries a bit that travels with
    the activation; ranking scales with how many *distinct* terms reached an
    entity. `ccode` and `sinc` both arriving at `CCodePrinter` is real evidence;
    one term shouting ten times is not, and summing scores cannot tell the
    difference.
  - **Unusual direct mention.** A term occurring in three or fewer entities
    repo-wide is a fingerprint, not a keyword. It is also the only way an
    entity joined to the issue by *no edge at all* gets retrieved — the test
    for this ranks a function first because it is the sole place in the repo
    saying `qdp`.
- **`hybrid` / `hybrid_walk`** — reciprocal-rank fusion of lexical with each map
  arm. If the map only helps when fused, that is the finding and these arms are
  how it shows up. `hybrid_walk` is the configuration the evidence argues for:
  BM25 orders files, the walk supplies function-level answers, at BM25's speed.
- **`random`** — the control. Not a contender; it is there so every other number
  on the page has a floor to be read against.

## Tuning, and why the numbers survive it

```bash
python -m bench.tune --limit 33 --objective mrr     # development set only
```

`bench.tune` **refuses to run on Verified** — that is an argparse guard with a
test behind it, not a promise in a README. Lite is the development set,
Verified is reported once, and `config_hash` in every result row lets a reader
confirm the reporting run used the frozen config rather than one refitted after
seeing the answers.

The grid is deliberately small (54 cells). A 200-cell search over 33 instances
does not find good parameters; it finds whichever cell suited two or three
issues. `tuning.json` records **every** config tried, not just the winner, and
the tool prints the top-5 spread — when that spread is noise, it says so.

What the first search found is worth repeating, because it is the kind of
result a benchmark exists to produce: **tuning gained 0.009 MRR against a
top-5 spread of 0.013, and `recall@1` did not move in any of the 54 cells.**
The shipped configuration is therefore the untuned default, and the reported
number carries no tuning debt at all.

Candidate sets are identical across arms (non-test Python files), so the
comparison is over ranking, not over who searched a bigger haystack.

## How the oracle works

`bench/truth.py` builds ground truth from the gold patch with stdlib `ast` and
its own diff parser — deliberately **not** with the CodePulse engine, and not
with `codepulse.delta`. A grader sharing a parser with the thing it grades
cannot catch that parser being wrong: an entity the engine can't see has to
count against the engine, not disappear from the denominator.

- Old-side hunk coordinates decide what "had to change"; the innermost
  enclosing function or class gets the attribution, so `Class.method` counts
  and `Class` does not (crediting both would inflate recall).
- The new side is reconstructed by applying the hunks, so a function the fix
  *added* is a target under its own name. Reconstruction is strict — a
  mismatched context line skips the instance rather than fuzzing it.
- Test files are excluded and recorded in `skipped_files`, never silently dropped.

## Reading the scorecard

- `recall@k` — fraction of gold files in the top k. The headline.
- `all_found@k` — every gold file in the top k. The strict one; quote this when
  it matters, since a fix spanning three files is not localized by finding one.
- `mrr` — reciprocal rank of the first gold file.
- `entity_recall@k` — same question at function grain. Only arms that rank
  entities have it; BM25 ranks files only, which is itself part of the point.
- `median s/instance` — sits next to accuracy on purpose. A retrieval win paid
  for with a 60× slowdown is not a win.

Skipped instances are printed with reasons and excluded from the denominator.
An accuracy number without its denominator is not a result.

## Limitations, stated up front

- **Localization is a proxy.** A correctly located bug can still be fixed
  wrongly. That gap is exactly what `exec_harness` exists to measure.
- **BM25 is a floor, not the state of the art.** Published localizers do
  better. The claim here is against grep-shaped retrieval, which is what the
  README compares to — not against the leaderboard.
- **Python only.** SWE-bench Lite is all Python, so this benchmark exercises
  one recipe. CodePulse's cross-language edges — the thing no single-language
  tool can see — are *not* measured here at all. That is a real gap in the
  evidence, not an oversight.
- **The map arm is unsupervised.** Seed weights and decay are coarse round
  numbers, chosen once and not fitted, so the score is a floor for the
  approach rather than its ceiling.
